# 阶段五 D6 · 覆盖升级、学习数据与部署恢复任务书

编写日期：2026-11-19。

当前代码基线：**0.3.106**，提交 `1d50bc8`；D1—D5 已实机验收通过，当前用户验收基线为 0.3.106。

本任务书只规划 D6，不在本轮修改代码、不构建 APK。D6 的目标不是增加输入法功能，而是证明：**升级不丢用户数据，部署失败不损坏数据，进程被杀后能恢复，发布包与调试包行为一致。**

---

## 一、为什么现在做 D6

D5 已完成符号页重排，核心输入链路和界面交互已有连续版本验收。下一步如果直接继续做主题、自定义或词库管理，风险会转移到数据层：

- 用户学习词是否真的写入用户目录，而不是只在当前进程有效；
- 覆盖安装新 APK 后，资源版本变化是否会覆盖用户词库；
- 部署过程被杀、写入中断、版本文件已写但事务尚未提交时，下一次启动是否能回到一致状态；
- 首次部署失败时，英文输入是否仍可用，是否会无限重试；
- 原生 Rime 已打开数据库时，是否错误地复制/恢复文件造成损坏。

D6 先把这些高风险边界锁住，再进入 D7 性能和稳定测试版。

## 二、当前实现事实，不重复开发

### 2.1 用户目录和资源目录已经分离

现有实现中：

- `BundledRimeData.install()` 把 APK 资源安装到版本化目录 `shared-<version>`；
- 内置资源有 `default.yaml`、`xyu_pinyin.schema.yaml`、`pinyin_simp.dict.yaml` 的 SHA-256 校验；
- 资源目录校验失败会重新从 assets 建立 staging 目录，不直接覆盖有效资源；
- `user/` 是用户目录，资源安装不会把用户目录当成 APK 资源覆盖；
- `RimeEngine.DATA_VERSION` 当前为 `pinyin-simp-0c6861e-3`；
- D6 要验证上述行为在真实覆盖安装和进程重建中成立，不重新设计资源结构。

### 2.2 部署已经有事务目录和恢复状态

`RimeDeployment` 当前使用：

- `deployment.preparing/`：准备快照阶段；
- `deployment.pending/`：已建立事务快照、等待提交或需要恢复；
- `state=pending`：新部署尚未提交；
- `state=committed`：新版本和用户数据已经完成提交，下一次冷启动只需要清理旧快照；
- `version`：当前资源版本；
- `shared-<version>/`：版本化共享资源；
- `user/`：当前用户目录。

已有 `begin()`、`commit()`、`recover()`、`initialize()`，并且 `recover()` 设计为可重复执行。

### 2.3 已有测试不能直接等同于 D6 完成

当前已有：

- JVM 部署故障注入：备份、恢复、首次失败、恢复中断、提交后清理、同版本失败等场景；
- Android Rime 测试：候选、选词、用户词/生成句复用、重置、多个前端 owner、共享资源损坏重装、用户 sentinel 保留；
- CI release APK 的签名、双 ABI、ZIP/ELF 16 KB 静态检查。

这些证明了很多局部逻辑，但仍不等于：

- 用户从旧 APK 覆盖安装到新 APK 后真实学习数据保留；
- 真实 Android 进程被强杀后恢复；
- 真实 release 包首次部署和升级部署都走通；
- 16 KB 内核上的动态库实际加载成功；
- 每个关键事务点的“杀进程—重新启动—再次恢复”都有证据。

D6 的工作重点是补这些**真实证据**，而不是重复已有 UI 或候选页开发。

## 四、核心数据不变量

任何 D6 代码或测试都必须围绕这些不变量，不以“程序没崩”作为通过标准。

### I1：用户目录不被资源安装覆盖

`user/` 中的测试用户词、用户配置和 sentinel 文件，在资源版本变化、共享资源重装、进程重建后仍存在且内容一致。

### I2：提交顺序不能倒置

只有在：

1. 新共享资源已复制并校验；
2. 原生库已初始化；
3. schema/字典可用性探针已通过；
4. 新用户目录状态已落盘；

之后，才允许把事务标记为 `committed` 和发布新 `version`。

### I3：失败不能留下半个当前状态

下一次启动后只能出现两种合法结果：

- 完整恢复到旧版本；或
- 完整保留已提交的新版本。

不得出现“version 指向新版本但 shared 不完整”“user 只有半份”“旧版本正在使用新用户目录”等混合状态。

### I4：恢复幂等

对同一故障现场连续执行 `recover()` 两次或三次，最终目录、版本和可输入结果相同；第二次不能再次删除有效用户数据。

### I5：原生句柄打开时不复制数据库

任何文件恢复、备份和目录替换都发生在 native shutdown 成功之后。shutdown 失败时保留事务现场并报告失败，不强行覆盖仍可能打开的数据库。

### I6：中文不可用不能拖垮英文

首次部署失败、升级失败或 Rime 加载失败时：

- 英文直输仍可用；
- 不无限自动重试；
- 用户可以主动重试中文部署；
- 不把旧组合文字补发到新输入框。

## 五、实施工作包

### D6-P0：建立版本、设备和证据基线

**目的**：先固定对照组，避免用不同构建或不同设备比较。

**执行**：

1. 固定旧基线 APK：0.3.106，记录 SHA-256、versionCode、签名证书摘要；
2. 构建一个只改变资源版本的测试候选，或增加测试专用 data-version/asset fixture，不把测试开关带入 release 用户路径；
3. 记录测试设备：型号、Android 版本、系统语言、字体、键盘位置、存储空间；
4. 建立每次测试的证据目录：`upgrade/<case-id>/`，只保存版本、结果、目录状态摘要和人工操作记录，不保存完整个人输入；
5. 规定每个用例都要有：安装前状态、操作、重启点、预期、实际、是否可重复。

**完成门槛**：同一旧 APK 在同一设备上可以重复安装并输入；没有使用用户主力数据。

### D6-P1：首次部署与资源校验

**目的**：证明没有历史目录时，首次启动能建立完整共享资源和用户目录。

**场景**：

| 用例 | 操作 | 预期 |
|---|---|---|
| F01 | 首次安装 0.3.106，启用输入法，首次切中文 | 共享资源完整、Rime 初始化一次、可离线输入 |
| F02 | 首次部署期间退出输入法，再次打开 | 不出现半目录，下一次可继续或干净重试 |
| F03 | 删除/损坏一个 shared staging 文件后重新初始化 | 重新安装资源，用户目录不被删除 |
| F04 | assets 资源校验失败注入 | 中文进入明确失败态，英文仍可输入，不无限循环 |
| F05 | 同一版本冷启动两次 | 第二次使用已校验资源，不重复破坏用户目录 |

**实现要求**：

- 资源校验只允许针对 staging/shared 目录；
- 失败日志不得包含正文或词库内容；
- 失败状态要能被测试读取，发布 UI 只显示无正文分类提示；
- 首次部署期间不能在主线程同步执行大量文件复制。

### D6-P2：学习词和用户数据持久化

**目的**：证明“学习成功”不是只存在当前 native session。

**测试数据**：

使用预先确定的、无个人信息的人工词组，例如当前已有测试中的 `nihaonihao` → `你好你好`；实际测试前确认该词组不是内置词典固定候选。不能使用用户真实姓名、联系人、聊天内容。

**场景**：

| 用例 | 操作 | 证据 |
|---|---|---|
| U01 | 输入人工词组，选中目标候选，正常结束输入 | 目标候选提交成功；记录候选索引/测试短语 ID，不记录私人正文 |
| U02 | 同一进程再次输入同一拼音 | 用户词/学习结果仍可提供；同时检查 reading/comment 与选词结果 |
| U03 | 关闭输入法服务或重建进程后再输入 | 结果仍可用，不依赖旧 session |
| U04 | 退出应用、重新打开、重新启用输入法 | 用户数据仍在，英文和中文都可用 |
| U05 | 覆盖安装新 APK 后重复输入 | 学习数据不被 shared 新资源或首次部署覆盖 |
| U06 | 用户目录放置 sentinel/custom 配置后升级 | 文件内容保留，资源版本文件正常变化 |

**证据要求**：

- 不能只用“候选排名还在”作为唯一证据，因为词典变化可能影响排名；
- 至少结合候选 comment/reading、用户目录摘要或测试专用导出探针；
- artifact 只放哈希、文件名、版本和 PASS/FAIL，不上传完整用户词库；
- 如果 JNI 当前没有安全的用户词查询接口，增加 debug/test-only 的计数或哈希观测，不把接口暴露给发布 APK。

**完成门槛**：U01—U06 全部通过，且升级前后用户目录摘要一致、shared 目录可变化。

### D6-P3：覆盖升级与资源版本变化

**目的**：分清“应用代码升级”和“资源数据升级”两类风险。

**升级链**：

```
0.3.106（旧包）
   ├─ A：代码/界面变化，DATA_VERSION 不变
   └─ B：测试资源版本变化，shared-<new> 新建
        ↓
新包覆盖安装，不卸载、不清数据
        ↓
首次启动/首次中文输入/重启
```

**A 路径**：

- packageName 不变；
- 固定签名一致；
- versionCode 增长；
- `user/` 不重建；
- shared 目录可复用；
- 学习词、用户配置仍可用。

**B 路径**：

- 新 shared 目录先 staging、校验再激活；
- 旧 shared 在新版本稳定可用前不能删除；
- 用户目录不复制回旧资源、不被空目录替换；
- 失败时可以回到旧版本或保留已提交的新版本，但不得混用。

**禁止**：

- 用卸载重装代替覆盖升级；
- 先清数据再说“保留成功”；
- 用 debug APK 结果代替签名 release 升级结果；
- 以“安装成功”代替用户词数据验证。

---

### D6-P4：部署阶段故障注入和恢复

**目的**：把每一个事务边界变成可重复测试，而不是只测一个总失败。

**故障矩阵**：

| 阶段 ID | 注入位置 | 重启后必须得到 |
|---|---|---|
| R01 | `deployment.preparing` 快照未完成 | 保留旧 user/shared/version，清理或继续可恢复 |
| R02 | `state=pending` 已落盘、资源未提交 | 恢复旧版本，pending 可幂等清理 |
| R03 | shared 新目录复制中断 | 旧资源可用，新 staging 不污染旧目录 |
| R04 | user 快照复制中断 | 旧 user 完整，不能用半份 user 替换 |
| R05 | native initialize 失败 | shutdown/恢复顺序正确，英文仍可用 |
| R06 | schema/字典可用性探针失败 | 不提交新版本，用户数据保留 |
| R07 | version 已写、state 尚未 committed | 下一次 recover 按事务事实恢复，不接受混合状态 |
| R08 | `state=committed` 后清理前被杀 | 保留新版本和用户数据，重复 recover 只清理旧快照 |
| R09 | restore 删除 user 后复制中断 | 下一次 recover 可继续，最终恢复完整旧 user |
| R10 | shutdown 失败 | 不在打开数据库上复制/删除；现场保留给下一次冷启动 |
| R11 | rename/fsync 报错 | 不盲目 fallback；依据 committed 状态决定恢复方向 |
| R12 | 同版本重复部署失败 | 不生成无限 pending，不破坏当前有效数据 |

**每个场景都执行**：

1. 注入一次；
2. 模拟进程被杀/测试函数中断；
3. 新进程调用初始化或 `recover()`；
4. 再调用一次 `recover()`；
5. 检查版本、目录摘要、用户 sentinel、中文/英文可用性；
6. 再重启一次，确认不是“只恢复了一次”。

**完成门槛**：R01—R12 至少有 JVM 证据；涉及 Android 文件系统、native handle 或真实进程的场景另有 Android/真机证据。不能只把异常捕获为 PASS。

---

### D6-P5：进程、服务和系统回收

**目的**：验证真实进程边界，不把普通 `reset()` 当成进程重建。

**场景**：

- 输入法服务正在中文组合时隐藏键盘；重新打开，旧组合不得补发到新框；
- 完成学习词后 force-stop 测试应用/输入法进程，再启动并输入；
- 在部署过程中终止测试进程，再启动；
- `RimeEngine.close()` 后新建 engine，旧 native session 不可继续回调；
- 两个 frontend owner 交替创建/关闭，不能让第二个 owner 读到旧 handle；
- `onDestroy`、系统回收、旋转和输入框切换不会产生重复部署线程；
- 进程重建后 pending/preparing/version.tmp 的清理结果稳定。

**证据**：

- Android `am force-stop`/重新启动记录；
- 输入法服务重新连接记录；
- 不记录正文，只记录 session/transaction ID、版本、阶段和结果；
- 强杀场景不在用户主力手机执行，使用可清空的测试设备。

---

### D6-P6：release 包和安装升级冒烟

**目的**：证明真正交付包而非 debug 包满足 D6。

**每个 D6 候选 APK 必须核对**：

- versionCode/versionName；
- packageName；
- 固定签名证书摘要；
- SHA-256；
- arm64-v8a 与 x86_64；
- Rime assets 校验；
- ZIP/ELF 16 KB 静态对齐；
- release 安装、首次中文输入、覆盖安装、重启后中文输入；
- 无 debug 测试入口、无测试故障注入按钮、无正文日志。

**交付包**：APK、SHA256SUMS、BUILD.txt、native-validation、D6 变更说明、验收卡、已知限制。

## 六、测试矩阵和执行顺序

### 第一层：本地/JVM，先跑

- `RimeDeploymentTest` 全部现有故障注入；
- R01—R12 分阶段 fault injection；
- `recover()` 连续执行 3 次；
- 共享资源 checksum、symlink/path traversal、版本字符串非法值；
- 用户目录 sentinel 保留、空目录和无历史版本首次部署。

### 第二层：Android debug，随后跑

- `RimeEngineTest` 扩展：学习词/用户数据、reset/close、新 owner、资源版本；
- 测试专用 D6 fixture：旧版本资源、新版本资源、唯一学习词 ID、故障注入点；
- force-stop 后新进程初始化；
- release-like 资产校验但不上传用户正文。

### 第三层：release + 覆盖安装，最后跑

设备使用可清空的 Android 16 realme RMX3852 或等价测试设备：

1. 安装 0.3.106；
2. 记录签名和版本；
3. 学习人工词组并重启验证；
4. 覆盖安装 D6 候选，不卸载、不清数据；
5. 首次启动、中文输入、再次重启；
6. 资源版本变化链路重复一次；
7. 检查失败事务残留和用户数据摘要；
8. 只在完成全部证据后交给用户主力设备复测。

### 依赖顺序

```
P0 基线/fixture
  ↓
P1 首次部署 + 用户数据持久化
  ↓
P2 覆盖安装 A/B 路径
  ↓
P3 R01—R12 故障矩阵
  ↓
P4 force-stop/服务重建
  ↓
P5 release 交付包
  ↓
用户实机验收
```

任何上游工作包失败，后续包只能做诊断，不能把结果写成通过。

## 七、红线和注意事项

1. 不在用户主力手机上注入中断、清数据、降级覆盖或破坏性存储故障。
2. 不把个人词库、完整日志、输入正文上传到 Actions artifact。
3. 不在 native 数据库仍打开时恢复文件；先 shutdown，shutdown 失败就保留现场。
4. 不用排名变化单独证明学习词保留。
5. 不把共享资源版本变化写成用户数据变化；两者必须分开验证。
6. 不用 debug 包、JVM 临时目录或“同包名安装成功”替代 release 覆盖升级。
7. 不增加无限自动重试；失败状态要可见、可重试且有上限。
8. 不把 D6 和性能、主题、自定义、用户词库导入混在一个版本。
9. 不改变 D1—D5 已验收的键盘布局和中文输入行为。
10. 任何失败恢复后至少再执行两次冷启动/恢复，确认幂等。

---

## 八、完成定义

D6 只有同时满足以下条件才能标记为完成：

1. 首次部署成功且断网可输入；
2. 人工学习词在当前进程、重启、覆盖安装后仍可用；
3. 资源版本不变和资源版本变化各有真实报告；
4. R01—R12 故障矩阵有证据，恢复至少重复两次结果一致；
5. 进程强杀/服务重建后无半提交、跨框补发和重复部署死循环；
6. 首次部署或升级失败时英文仍可用，中文失败可主动重试；
7. user/shared 目录、version、pending/preparing 的最终状态符合不变量；
8. release APK 签名、哈希、双 ABI、资源和 16 KB 静态检查通过；
9. 未上传私人正文/完整用户词库；
10. 用户在测试设备上完成 D6 验收清单并确认“没问题”；
11. `acceptance-d6.md`、README、roadmap、构建报告和 APK 已归档。

未满足第 10 条时，状态只能写“云端/测试设备通过，待用户实机验收”，不能写 D6 完成。
